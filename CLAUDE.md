# conta-verde

Open-source ERP for small businesses (inspired by cloud ERPs such as Conta Azul): a Rust API (`crates/`) and a React SPA (`web/`).
License: **AGPL-3.0-or-later** (ADR 0001). Never use the Conta Azul name, logo or screenshots in code, docs or UI.

Read `docs/macro-plan.md` for scope (the reference module map and release plan), `docs/roadmap.md` for
phase order and progress, and `docs/adr/README.md` for the index of decisions. A phase starts by
accepting the `proposed` ADRs it depends on.

## Commands

```bash
pnpm install                 # once: installs husky and enables the pre-commit hook
pnpm check                   # Rust fmt/clippy/tests plus web typecheck/tests (what the hook runs)
docker compose up -d db      # PostgreSQL for local runs and ignored tests
docker compose up -d mailpit # catches the e-mail the app sends, at http://localhost:8025 (SMTP on 1025)
export $(cat .env.example | xargs)
cargo test --workspace -- --ignored   # Postgres integration tests (need DATABASE_URL)
cargo run -p conta-verde-api
pnpm --filter conta-verde-web dev     # web app on http://localhost:5173, proxies /api to the API
pnpm dev                     # database + Mailpit + API + web on free ports, PUBLIC_URL set to the web's (also: pnpm db, pnpm api, pnpm web)
```

CI (`.github/workflows/ci.yml`) runs the same checks plus the ignored tests against a Postgres service, and builds the web app.
The pre-commit hook does not run ignored tests, so run them yourself when touching `infrastructure`.

## Web app (ADR 0005)

- `web/` is Vite + React + TypeScript; it talks only to `/api/*`, which the Vite dev server (and a reverse proxy in production) forwards to the API with the prefix removed. Same origin means the session cookie works and no CORS is needed. Never add permissive CORS with credentials.
- `VITE_API_TARGET` points the dev proxy at the API (default `http://127.0.0.1:3000`). `VITE_SOURCE_URL` sets the footer's "Source code" link at build time; forks running modified code must point it at their own source (AGPL section 13).
- Keep the footer link and the API contract in `web/src/api.ts` in sync with the Rust DTOs by hand; there is no generated client yet.
- Tests are Vitest + Testing Library with `fetch` stubbed; prefer asserting what the user sees.
- Animation is Motion (`motion/react`) and icons are vendored Lucide Animated components in `web/src/components/icons/` (ADR 0016). Do not edit those by hand beyond the documented tweaks; to add one, download its registry JSON from `https://lucide-animated.com/r/<name>.json`, check it (only `motion/react`, `react` and `cn` imports, no network or DOM access) and replace the `@/lib/utils` import with `../../lib/utils`.
- A list page keeps its search, filters and order in one state object and gets its rows from `usePagedList` (`web/src/lib/usePagedList.ts`): it loads a first page again when the debounced values change, drops replies to an earlier request, and always sends a cursor with the same parameters that produced it. Use `ListRow` for rows and `History` (with a loader and labels) for a record's trail.
- Amounts the web adds or splits (the installments of an entry) are held as whole cents in a `bigint` (`web/src/lib/entryInstallments.ts`), never as a `Number`; the remainder goes to the last installment.
- Use `components/Button` for buttons (it plays its icon on hover/focus and shows a spinner while `pending`); the actions that repeat on every row pass `iconOnly` (its children stay as the tooltip and the accessible name, so tests still find it by `aria-label`). A record's active flag is a `StatusBadge`. Pages animate on enter only, and `Layout` remounts `<main>` on every path change, so page state never leaks across routes.
- The visual language is in `docs/design/` (tokens in `web/src/styles.css`, ADR 0020). Pages use `PageHeader`; signed-in pages sit in the sidebar shell from `Layout`, which reads the company from the URL. Dashboard figures come from `web/src/dashboard/sampleData.ts` until Phase 2, and charts are SVG components in `web/src/components/charts/`: print amounts only through `formatMoney`, and use `toDrawing` (`lib/chart.ts`) solely to place marks. Change the artboards in `docs/design/canvas/` with a token or screen change.
- The logo is `web/public/favicon.svg`, mirrored by `LogoMark` in `web/src/components/Logo.tsx`; change both together. The PNG and ICO favicons are rendered from the SVG.
- A browser pane or tab that is not painting never advances `requestAnimationFrame`, so animations look frozen at their first frame; that is the environment, not the app. Use a visible tab when checking motion.

## Architecture (ADR 0002)

One crate per layer; dependencies point inwards and the compiler enforces it.

| Crate | Holds | Depends on |
|-------|-------|------------|
| `domain` | Entities, value objects, rules. No I/O, no serde, no sqlx. | `uuid`, `rust_decimal` |
| `application` | Use cases (`*Service`) and port traits (`*Repository`). | `domain`, `uuid` |
| `infrastructure` | Adapters implementing ports: Postgres (sqlx) and in-memory. | `application`, `domain` |
| `api` | axum routes, request/response DTOs, `main.rs` wiring. | all |

Rules that are easy to break:
- `api` must not import `sqlx`; anything database-related lives in `infrastructure`.
- Adapter behavior is specified once in `crates/infrastructure/src/contract.rs` and run against both adapters; extend it when adding a port.
- The API names its adapters once, in a `Ports` trait with an associated type per adapter (`crates/api/src/lib.rs`); handlers are `fn handler<X: Ports>(State<SharedState<X>>, ...)`. A new register adds an associated type, a field in `Services` and `AppState`, and the type in `PostgresPorts` (`main.rs`) and in the test ports; never another type parameter.
- Use cases are generic over their port (`PartyService<R: PartyRepository>`), not `dyn`. Port methods return `impl Future + Send`.
- Serde types belong in `api`. Domain types are not serialized directly.
- Every business table has `company_id`, every repository method takes a `CompanyId`, and uniqueness is scoped by company (ADR 0004).
- Every write to a business table carries an `AuditEntry` built by the use case (actor from `CompanyAccess`, field changes from `domain::audit`) and stored in the same transaction (ADR 0008). A new register needs its entity in `AuditEntity`, both adapters recording it, and a contract test that a refused write leaves no entry. Never audit account, session or membership writes, and never edit or delete `audit_log` rows (a trigger forbids it).
- List endpoints take `limit`, `after`, `q`, one closed-value parameter per filter and `sort` (`field` or `-field`), through a `*Query` type both adapters implement; unknown values are `400` JSON, never ignored (ADR 0018). Sort only by non-null columns ending in the id, so the keyset cursor stays valid. Bind search text with `strpos`, never `LIKE`.
- Money is exact decimal (`rust_decimal` / `NUMERIC`), never floats (ADR 0003). In `domain` it is `Amount`: strict parsing, never rounded, no trailing zeros; the API sends and takes decimal strings, and the web app never converts one to a `Number` (`web/src/lib/decimal.ts`).
- Categories are a tree (ADR 0012): only a root chooses the DRE and cash-flow groups, a subcategory inherits them, and the parent and groups never change. The category for transfers is the root in the `transfers` group, found by that group and never by its name. An active category is never under an inactive one (checked by the use case, not the database). The group keys are stored in CHECKs and the audit trail; do not rename them.
- The cash flow (ADR 0032, `BalanceService::cash_flow`, `GET /cash-flow?from=&to=&granularity=&account=`) is composed from the ports like the balances: per account, `cash_by_day` (entries' port) and `movement_by_day` (transfers' port) from the account's opening day, then cut into day or calendar-month periods in the use case, with a running balance that starts from the balance of the day before `from` and takes each opening balance in on its day. The forecast is `open_by_due_day` (what is left of installments, by due date), only for every account together (an installment has no account), and what fell due before `from` is `past_due`, counted by the projected balances. At most 400 days or 60 months (`InvalidSpan`, `400`); the client sends the dates.
- The reports (ADR 0035, `FinancialEntryService::report` and `overdue`, `GET /reports/entries` and `/reports/overdue`, `finance`, read only) are sums made by the entries' port (`report_entries`, `overdue_installments`) in SQL and in memory: the entries grouped by category, cost center or party over a span `from`..`to` (both required: the server reads no clock), on the **competence** basis (the entries whose competence date is in it, by their total) or the **due** basis (the installments due in it, by their amount); rows biggest first and what has no cost center or party last (`sort_report`), amounts as entered and not as settled. The overdue list is the installments due **before** `on` with something left (amount less the settlements that are not reversed), oldest first, cut at `limit` (100 by default, 500 at most) with the totals of all of them.
- An attachment (ADR 0036, `Attachment`, `AttachmentService`, routes under `/entries/{id}/attachments`, `finance`) is a record in `entry_attachments` (name, listed type, 1 byte to 10 MB, `removed`) whose **bytes live in a `BlobStore`** (`LocalBlobStore` in `ATTACHMENTS_DIR`, `InMemoryBlobStore`) under the company and attachment ids, never a typed name. It is never edited or deleted: removing marks it, drops the bytes and audits both. The bytes are written before the record (a failed record write takes them back) and dropped after it is marked. The file is the **body of the request**, its type the `Content-Type` and its name `?name=` (no multipart); a download is always `attachment` with `nosniff`. At most 20 per entry, counted by the use case.
- The lines of a quote, sale or contract (ADR 0037, `Line`, `LineDraft`) are a product, a description kept as typed, a quantity above 0 with at most 3 decimals, a unit price with at most 6 and a discount in cents; a line is worth `round_to_cents(quantity x price) - discount` (the one rounding rule of sales, half away from zero, in `domain`; `web/src/lib/saleLines.ts` does the same in `bigint` and a test holds them to the same cases), and a document's total is the sum of its lines and is never stored. A document has 1 to 100 lines, replaced as a whole with the document in one transaction. Numbers (`Quote`, later `Sale`) are the company's own sequence, taken from `document_counters` inside the write that uses them (`next_document_number`), so a failed write gives its number back. What a sales document points at is asked through `SalesReferences` (`RegisterSalesReferences`), and only a reference an edit changes is checked.
- A quote (ADR 0038, `Quote`, `QuoteService`, routes under `/quotes`, area `sales`) is a draft, sent, approved, declined or converted. Changing a sent quote makes it a draft and takes its link back; sending again makes a new link; an answered or converted quote is fixed (`409`). Every write names the status it was made from (`QuoteChanged`, `409`), and the customer's answer (`QuoteRepository::answer`) writes only the status and only through the same link, so it never overwrites an edit nor approves what was changed and sent again; whether a quote changed is decided on the quote (`after == before`), never on the audit text. The link is `{PUBLIC_URL}/quote/{token}` with only the SHA-256 digest of the token stored, shown once in the send's answer; the public routes show no id of the company's books, approve or decline once, refuse an approval past `valid_until` (`410`; a decline is still allowed, and sending an expired quote is refused), judged against **yesterday by the UTC clock** (`customer_today`: UTC turns the day at 21:00 in Brazil; the one place besides the recurrence job where the server reads the clock), answer with `no-store` and `no-referrer` and record it under whoever sent the quote with an `answered_by` change (the trail never holds the customer's e-mail address). The PDF is written by hand in `api/src/quote_pdf.rs` (WinAnsi, tested byte by byte); the e-mail carries the link only.
- A sale (ADR 0039, `Sale`, `SaleService`, routes under `/sales`, area `sales`) is an `open` order (the only state that changes), a `completed` sale or a `cancelled` one. Completing validates the receivable first (`FinancialEntryService::validate`), then marks the sale, then writes the entry with origin `EntryOrigin::Sale`; a unique index gives a sale one entry, so completing is idempotent and asking again finishes an entry a failure left unmade. The receivable is split by `PaymentTerm::split` (each share cut to the cent, the last takes the remainder; none without a term: one installment on the sale's day; `web/src/lib/termSplit.ts` previews it with the same cases). An entry can be cancelled once and for good (`voided`, `FinancialEntryRepository::void`, `FinancialEntryService::void`): refused while a settlement is not reversed (`EntrySettled`), out of the open amounts, the overdue list and the reports by group in **both** adapters, listed with `voided=true|false`, never edited or settled; cancelling a completed sale voids its receivable first and is refused while it has settlements or returns. A transition writes only the status (`SaleRepository::set_status`, under the sale's lock, cancelling refused with `SaleHasReturns` there), and a return is stored only while the sale is completed and has the returns the refund was worked from (`save_return(known_returns)`); what a sale or a return made is not edited as an entry (`EntryFollowsASale`). The lines in the audit trail are one per row (`\n`), the description last. A return takes back at most what was sold and not returned (checked by the adapter with the sale locked), refunds each line cumulatively rounded, and makes a payable with origin `SaleReturn` (the return is stored first, so only a storage failure leaves one without its refund); it never reduces the receivable. `EntryOrigin` is an enum (`Recurrence`, `Sale`, `SaleReturn`) with a CHECK of at most one origin and a unique index per origin (`DuplicateOrigin`). A quote becomes one sale (`POST /quotes/{id}/convert`, a unique index on `sales.quote_id`; asking again gives that sale).
- A contract (ADR 0040, `Contract`, `ContractService`, routes under `/contracts`, area `sales`) bills each cycle **on its day** as a completed sale (`SaleService::bill_cycle`): `starts_on` plus 0, 1, 2… cycles of 1, 2, 3, 6 or 12 months by `CalendarDate::plus_months` (the day clipped, never slid), at most one sale per cycle day (unique index on `sales (contract_id, cycle_on)`, `DuplicateCycle`), and a cycle that already has its sale is only finished, so a pass is safe to repeat and to run twice. It runs when a contract is written (server `today()`) and in an hourly task in `main.rs`; `bill_all_due(day)` takes the day, so tests move the clock, and its report counts the contracts of every company (assert on one company's sales, not on the report). `billed_through` is bookkeeping written without an audit entry; a paused contract that is brought back goes on from today; a terminated one is fixed (`ContractIsTerminated`, `409`) but still bills the cycles due up to its last day; a cycle whose sale was cancelled is consumed; the job re-reads each contract and bills up to `customer_today()`. `adjust` raises every unit price by a percentage rounded to the cent (`round_to_cents`) for the cycles billed from then on. The sales are made in the name of whoever last saved it.
- A commission rule (ADR 0041, `CommissionRule`, `CommissionService`, routes `commission-rules` and `GET /commissions?from=&to=&seller=`, `sales` area) is a rate (above 0 to 100, two decimals) for one seller or all and one product or all, over the sale days `starts_on`..`ends_on`; it is replaced as a whole by `PUT` (`active` required), never deleted, and **a new rate is a new rule that starts later**. The rule for a line is the narrowest that covers the sale's own day (seller and product, seller, product, general; ties by later start, then id; inactive ignored). The statement is computed on every read, never stored, from the completed sales **with a seller** sold in the span (both dates required, at most 2000 sales) through the sales' port (`sold_between`, `returns_of_sales`), per line `round_to_cents(net × rate / 100)` with the net being the line less its cumulative refund; a line no rule covers earns nothing but counts in the base.
- A price list (ADR 0042, `PriceList`, `PriceListService`, routes `price-lists`, `sales` area) is a name (unique per company, ignoring case), an `active` flag (required when replacing) and 1 to 1000 prices (a product once, a unit price of at most six decimals), replaced as a whole with the list in one transaction (`price_list_items`, composite company FKs). Only a product a change adds must be usable. It is **not part of any document**: lines keep the price they were filled with, and the web `LinesEditor` fills a line's price from the list chosen (falling back to the product's sale price) on the client, without sending the list.
- A sales report (ADR 0043, `SalesReportService`, `GET /sales-reports?by=customer|product|seller&from=&to=`, `sales` area) is added up when read from the completed sales of a span net of returns (both dates required, at most 2000 sales, composed from the sales' port like the commissions and never as SQL in two adapters). The net of each line is the one domain function `net_of_lines`, shared with `commission_of_sale`. Rows are biggest first (no seller last), with their share and cumulative share (two decimals) and an ABC class given by the cumulative share **before** the row (A under 80%, B under 95%, else C), worked out from the exact values.
- A statement line (ADR 0034, `StatementLine`, `ReconciliationService`) is what a bank's OFX file says: a signed non-zero amount in cents, a day, a one-line description, and a status that only moves between `pending`, `matched` (to exactly one settlement **or** one transfer) and `ignored`; it is never edited or deleted, and each move is audited. The import takes the OFX as it is (`parse_ofx` in `infrastructure`, UTF-8 or Latin-1, `import_rows` like the CSV imports); a **fingerprint** (day, amount, description, reference and the place among identical lines of the file) with a unique index per account makes sending a file twice add nothing. Suggestions come from `settlement_candidates` (entries' port) and `transfer_candidates` (transfers' port): same account, same cash or amount, direction by sign, within 5 days, not reversed, not matched (unique indexes keep one line per target). Creating an entry from a line registers it, settles it on the day and matches it in separate audited writes. The routes are `statement-lines` and `bank-accounts/{id}/statement-import`, both `finance`.
- A recurrence (ADR 0033, `/companies/{id}/recurrences`, `RecurrenceService`) is a register that becomes ordinary entries with one installment each, up to 60 days ahead of today, never past `ends_on`: `starts_on` plus 0, 1, 2… periods, a month counted **from `starts_on`** with the day clipped (the 31st is never slid to the 28th for good). The entry carries `recurrence_id` and `occurrence_on`, and a **unique index** makes at most one per occurrence day, so generating twice or in two places is safe (`DuplicateOrigin` is skipped); entries are made in the name of whoever last saved the recurrence (no system actor in the audit trail yet), and `generated_through` is bookkeeping written without an audit entry. It runs when a recurrence is saved (the server's UTC `today()`, the only place the server reads a clock) and in an hourly task spawned in `main.rs`; there is no `jobs` table because the pass is idempotent. A recurrence whose entries cannot be made (its category was deactivated) is skipped and retried, the others go on.
- Bank accounts keep no balance: it is added up on every read (ADR 0031) from the account's opening balance (its own record, signed, set by `PUT .../opening-balance`), the cash of its settlements that are not reversed (receivable adds, payable takes off) and its transfers in and out, counted from the opening day through the day asked (before it the balance is 0, without an opening everything counts). `BalanceService` composes it from the ports (`FinancialEntryRepository::cash_of_account`, `TransferRepository::movement_of_account`), never one query across tables, so both adapters answer alike; `GET /balances?on=` takes a required date because the server never reads a clock. A transfer moves money between two usable accounts, is not an entry (no category, nothing in the income statement), and like a settlement is reversed, never edited or deleted. Their branch and number are stored in one form (upper case letters and digits, no punctuation) because a unique index and, later, OFX matching depend on it; never store them as typed. Their kind, like a product's, is fixed once registered (ADR 0021).
- A financial entry (ADR 0029) has one category (active, never the transfers one), an optional cost center and party, a competence date and 1 to 120 installments (a due date that never decreases, an amount above 0 in cents); its total is the sum and is never stored. It is replaced as a whole by `PUT`, and the use case checks what it points at through `EntryReferences` (`RegisterReferences` asks the registers' own ports, so one implementation serves Postgres and memory: the in-memory registers are `Clone` over an `Arc` for that), while the database refuses a reference to another company with composite foreign keys. Dates are `CalendarDate` (`YYYY-MM-DD`, no zone, `DATE` in Postgres through text), never a timestamp. There is no delete or cancel yet; what an entry may still change once settled is the next slice's decision.
- A settlement (ADR 0030) pays one installment of an entry: `applied` (the part of the installment it settles, above 0), `interest`, `fine` and `discount` (0 or more, in cents) and a bank account (and optionally a method) that must be usable; the cash is `applied + interest + fine - discount` and is never stored, and neither is an installment's balance. It is never edited or deleted: `DELETE` reverses it (`reversed`), it stops counting and the trail keeps it. The check against the balance, the write and the audit entry are one transaction in the entry's port (`settle`): the installment row is locked **in a statement of its own and the balance read in the next one**, because in READ COMMITTED a sum read in the statement that waits for the lock uses the snapshot from before the wait (a concurrency test found it). While an entry has settlements that are not reversed its installments and kind cannot change (`409`), enforced by the adapters inside `update`. "Overdue" is told by the web app with today's date where the person is; the server never reads a clock for it.
- A payment term's installments are replaced as a whole in the transaction that writes the term and its audit entry, and their sum (exactly 100) and order live only in the domain: the database does not see them (ADR 0021). Percentages are strings with at most two decimals, never rounded; the web form fills equal shares with the remainder on the last.
- A party is replaced as a whole (`PUT`), and the registry is asked about its CNPJ only when the document changed; the same document keeps the old answer. `is_carrier` and `is_seller` must be said when replacing, so an old client cannot drop them. The address is all or nothing, in the domain and in a `CHECK`, and only its shape is checked (ADR 0022). Contacts (up to 20, in order) and tags (up to 10, lower case, no register) are replaced as a whole by the same `PUT`, must be said when replacing, and are read with the party in one `REPEATABLE READ` snapshot (`postgres::snapshot`); whether the contacts changed is decided on the contacts, never on the audit text (ADR 0023).
- A new register copies the products one (ADR 0019): a domain type that validates and normalizes, a port with a contract test (scoping, atomic audit, refused writes leave no trace), an adapter pair, a `PUT` that replaces and audits only the difference, and a `CHECK` in the migration for every domain rule so the database refuses what the domain would. The migration repeats the rules one row can show (shapes, key lists, lengths, uniqueness), not those that span rows, and its comments and the docs say which is which. A value the domain accepts must be one Postgres accepts too (NUL bytes were the case that bit).
- SQL uses runtime `sqlx::query`, not `query!` macros. Do not add `query!` without also solving offline data for CI.
- A new adapter or port method needs both adapters (Postgres and in-memory) to behave the same, including ordering.

## Gotchas

- Auth is cookie sessions (ADR 0007). Every `/companies/{company_id}/...` handler must take the `CompanyAccess` extractor (before any `Json`/`Query`); missing sessions get `401`, non-members and unknown companies both get `404`, and a member whose role does not reach the route gets `403`.
- An invitation's link carries a 256-bit token whose SHA-256 digest is all the database keeps, is shown once, and gives nothing by itself: accepting needs the session of the address it was sent to, or a sign-up through the link (`invitation` instead of `company_name` in `POST /auth/register`, which makes no company of its own) (ADR 0027). `GET /invitations/{token}` and the quote routes under `/public/quotes/{token}` (ADR 0038) are the only routes that need no session. Sending the e-mail never fails the invitation (`EmailSender`, ADR 0014): `SMTP_URL` and `SMTP_FROM` (both or neither, or the server does not start) send it through `SmtpEmailSender`, and without them the log adapter only logs it and says it was not sent, and the log then holds the link. Tests never reach a mail server: use `InMemoryEmailSender` or the fake SMTP server in `smtp_email_sender.rs`. Tokens come from `SecretService::new_token` and are stored as `digest_token`, never raw.
- What a role may do is decided by `CompanyAccess` from the **route**, not by the handler (ADR 0026): the area is the segment after `{company_id}` and the access is the method (`GET` reads, anything else writes). A new family of company routes needs its segment added to `area_of` in `access.rs`, or it is refused to everybody (`quotes` and the other sales segments are in the `sales` area, ADR 0037); the table is `Role::access_to` in the domain, and the web app reads `permissions` from `/auth/me` instead of knowing it: a register page gates its form, import and edit buttons on `useCanWrite(area)` (`web/src/lib/useCanWrite.ts`), which only spares the person a refusal.
- Not built yet: password reset, login rate limiting, handing a company over. A company has one owner, never changed or removed, which is what keeps it from being left without one (ADR 0028); `PATCH`/`DELETE /companies/{id}/members/{user_id}` change a role or end a membership, and the adapters refuse the owner themselves (`role <> 'owner'`). The API still binds to `127.0.0.1` by default and needs a TLS proxy plus `COOKIE_SECURE=true` before being exposed. Do not change the default bind address.
- The foreign key `parties.company_id -> companies` fails on old dev databases holding orphan parties: `docker compose down -v` resets it.
- Secrets (Argon2, token generation and digests) sit behind the `SecretService` port; the `argon2` crate is optimized even in dev builds (workspace `Cargo.toml`), or tests would take seconds per login.
- Migrations live in `crates/infrastructure/migrations/`. Do not edit one that has been merged to `main`; add a new one.
- Editing an applied migration locally breaks your dev database checksum: `docker compose down -v` resets it.
- Companies that have audit rows cannot be deleted in a dev database: `audit_log` references them and a trigger forbids deleting or updating its rows. Reset with `docker compose down -v` instead of `DELETE`.
- Storage errors are logged server-side and returned to clients as a generic `internal error`. Keep it that way.
- Documents are stored without punctuation and validated with check digits in `domain`: a CPF is 11 digits; a CNPJ is 14 characters whose first 12 may be uppercase letters (alphanumeric CNPJ, since July 2026). Never assume a document is numeric (no `inputMode="numeric"`, no digit-only parsing).
- A CNPJ is also looked up in the federal registry (ADR 0017); a CPF never is. Nothing the registry says blocks a registration: `NotFound` stores the party as `NotFound` with a warning (its data lags, so new companies can be missing), an outage stores it as `Unverified`, and `CNPJ_LOOKUP=off` (`Disabled`) stores it as `NotApplicable` without nagging. The port takes a `Cnpj`, which only `Document::cnpj` can build. Tests must never call the real service: use `InMemoryCnpjRegistry` or the local fake in `brasil_api.rs`. The real BrasilAPI answers 429 to requests without a `User-Agent`, and to callers that exceed its rate limit.
- An import (ADR 0025, parties and products, one pipeline `import_rows` in `application`) checks every row before writing any, refuses the whole file if one row is refused, then writes row by row (each with its own audit entry) and **skips** a row whose document or SKU is registered, never overwriting. A price may use a decimal comma (`12,50`) and nothing else beyond the strict amount. It does not ask the CNPJ registry (`Unverified`, or `NotApplicable` when `CnpjRegistry::is_enabled` is false). CSV is read in `api` (`csv_import.rs`); use cases take drafts and know nothing of CSV.
- A CEP is looked up only when the person presses "Buscar endereço" (ADR 0024): `GET /companies/{id}/postal-codes/{code}`, nothing stored or audited, `CEP_LOOKUP=off` switches it off. BrasilAPI answers `404` both for an unknown code and when its own sources are down, so a `404` proves nothing; the port takes a `PostalCode`, and a code that is not eight digits is refused before the directory is asked. Tests use `InMemoryPostalCodeDirectory` or the local fake in `brasil_api_postal_code.rs`.

## Conventions

- Reply to the user in Brazilian Portuguese. Code, identifiers, commits, branch names and user-facing docs are in **English**.
- Commits and branches follow semantic prefixes (`feat`, `fix`, `docs`, `refactor`, `chore`, `test`), e.g. `feat/accounts-payable`.
- Comments explain why, not what. No dead code, no premature abstraction.
- Tests before refactoring. Run `pnpm check` before declaring work done.
- Docs under `docs/` start with frontmatter: `title`, `status`, `date`, `tags`. ADRs are `docs/adr/NNNN-slug.md`; record significant decisions as a new ADR.

## Workflow

- Work in a git worktree on a semantic branch, push with `gh`, open a PR to `main` (GitHub flow).
- **Review is local**: run `/code-review` on the branch and fix the findings before asking for merge. Do not wait for the Copilot reviewer.
- Documentation-only PRs (ADRs, `docs/`, CLAUDE.md) may be merged right after the push.
- Use `pnpm` for Node tooling and `uv` for Python, if either is ever needed.
