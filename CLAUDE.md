# conta-verde

Open-source ERP for small businesses (inspired by cloud ERPs such as Conta Azul): a Rust API (`crates/`) and a React SPA (`web/`).
License: **AGPL-3.0-or-later** (ADR 0001). Never use the Conta Azul name, logo or screenshots in code, docs or UI.

Read `docs/macro-plan.md` for scope (the reference module map and release plan), `docs/roadmap.md` for
phase order and progress, and `docs/adr/README.md` for the index of decisions. A phase starts by
accepting the `proposed` ADRs it depends on.

## Commands

```bash
pnpm install                 # once: installs husky and enables the pre-commit hook
pnpm check                   # Rust fmt/clippy/tests plus web typecheck/tests (what the hook runs)
docker compose up -d db      # PostgreSQL for local runs and ignored tests
docker compose up -d mailpit # catches the e-mail the app sends, at http://localhost:8025 (SMTP on 1025)
export $(cat .env.example | xargs)
cargo test --workspace -- --ignored   # Postgres integration tests (need DATABASE_URL)
cargo run -p conta-verde-api
pnpm --filter conta-verde-web dev     # web app on http://localhost:5173, proxies /api to the API
pnpm dev                     # database + Mailpit + API + web on free ports, PUBLIC_URL set to the web's (also: pnpm db, pnpm api, pnpm web)
uv run scripts/e2e-accountant.py http://127.0.0.1:3000   # the exit criterion of Phase 6 against a running API (see the script)
```

CI (`.github/workflows/ci.yml`) runs the same checks plus the ignored tests against a Postgres service, and builds the web app.
The pre-commit hook does not run ignored tests, so run them yourself when touching `infrastructure`.

## Web app (ADR 0005)

- `web/` is Vite + React + TypeScript; it talks only to `/api/*`, which the Vite dev server (and a reverse proxy in production) forwards to the API with the prefix removed. Same origin means the session cookie works and no CORS is needed. Never add permissive CORS with credentials.
- `VITE_API_TARGET` points the dev proxy at the API (default `http://127.0.0.1:3000`). `VITE_SOURCE_URL` sets the footer's "Source code" link at build time; forks running modified code must point it at their own source (AGPL section 13).
- Keep the footer link and the API contract in `web/src/api.ts` in sync with the Rust DTOs by hand; there is no generated client yet.
- Tests are Vitest + Testing Library with `fetch` stubbed; prefer asserting what the user sees.
- Animation is Motion (`motion/react`) and icons are vendored Lucide Animated components in `web/src/components/icons/` (ADR 0016). Do not edit those by hand beyond the documented tweaks; to add one, download its registry JSON from `https://lucide-animated.com/r/<name>.json`, check it (only `motion/react`, `react` and `cn` imports, no network or DOM access) and replace the `@/lib/utils` import with `../../lib/utils`.
- A list page keeps its search, filters and order in one state object and gets its rows from `usePagedList` (`web/src/lib/usePagedList.ts`): it loads a first page again when the debounced values change, drops replies to an earlier request, and always sends a cursor with the same parameters that produced it. Use `ListRow` for rows and `History` (with a loader and labels) for a record's trail.
- Amounts the web adds or splits (the installments of an entry) are held as whole cents in a `bigint` (`web/src/lib/entryInstallments.ts`), never as a `Number`; the remainder goes to the last installment.
- Use `components/Button` for buttons (it plays its icon on hover/focus and shows a spinner while `pending`); the actions that repeat on every row pass `iconOnly` (its children stay as the tooltip and the accessible name, so tests still find it by `aria-label`). A record's active flag is a `StatusBadge`. Pages animate on enter only, and `Layout` remounts `<main>` on every path change, so page state never leaks across routes.
- The visual language is in `docs/design/` (tokens in `web/src/styles.css`, ADR 0020). Pages use `PageHeader`; signed-in pages sit in the sidebar shell from `Layout`, which reads the company from the URL. The dashboard (ADR 0043, `pages/DashboardPage.tsx`) is built on the client from the existing finance and sales endpoints, **one card per request** (`dashboard/useLoaded.ts`), each in a `CardBoundary` so a card that fails or cannot be drawn says so alone; it sends today's date (`todayIso()`, the server reads no clock), stamps "Atualizado em" and has no sample data. Charts are SVG components in `web/src/components/charts/`: print amounts only through `formatMoney`, and use `toDrawing` (`lib/chart.ts`) solely to place marks. Change the artboards in `docs/design/canvas/` with a token or screen change.
- The logo is `web/public/favicon.svg`, mirrored by `LogoMark` in `web/src/components/Logo.tsx`; change both together. The PNG and ICO favicons are rendered from the SVG.
- Explanations sit behind an (i), not in a paragraph (`docs/design/screen-anatomy.md` section 4): a page's `PageHeader` `description`, a card's or form section's `HelpTitle`, a chart's `ChartCard` description, a control's `InfoTip` in an `action-with-tip` row. Errors, consequences to know before pressing, empty states, data and format hints under a field stay in sight; `PageHeader` `subtitle` is for facts about what the page shows.
- A browser pane or tab that is not painting never advances `requestAnimationFrame`, so animations look frozen at their first frame; that is the environment, not the app. Use a visible tab when checking motion.

## Architecture (ADR 0002)

One crate per layer; dependencies point inwards and the compiler enforces it.

| Crate | Holds | Depends on |
|-------|-------|------------|
| `domain` | Entities, value objects, rules. No I/O, no serde, no sqlx. | `uuid`, `rust_decimal` |
| `application` | Use cases (`*Service`) and port traits (`*Repository`). | `domain`, `uuid` |
| `infrastructure` | Adapters implementing ports: Postgres (sqlx) and in-memory. | `application`, `domain` |
| `api` | axum routes, request/response DTOs, `main.rs` wiring. | all |

Rules that are easy to break:
- `api` must not import `sqlx`; anything database-related lives in `infrastructure`.
- Adapter behavior is specified once in `crates/infrastructure/src/contract.rs` and run against both adapters; extend it when adding a port.
- The API names its adapters once, in a `Ports` trait with an associated type per adapter (`crates/api/src/lib.rs`); handlers are `fn handler<X: Ports>(State<SharedState<X>>, ...)`. A new register adds an associated type, a field in `Services` and `AppState`, and the type in `PostgresPorts` (`main.rs`) and in the test ports; never another type parameter.
- Use cases are generic over their port (`PartyService<R: PartyRepository>`), not `dyn`. Port methods return `impl Future + Send`.
- Serde types belong in `api`. Domain types are not serialized directly.
- Every business table has `company_id`, every repository method takes a `CompanyId`, and uniqueness is scoped by company (ADR 0004).
- Every write to a business table carries an `AuditEntry` built by the use case (actor from `CompanyAccess`, field changes from `domain::audit`) and stored in the same transaction (ADR 0008). A new register needs its entity in `AuditEntity`, both adapters recording it, and a contract test that a refused write leaves no entry. Never audit account, session or membership writes, and never edit or delete `audit_log` rows (a trigger forbids it).
- List endpoints take `limit`, `after`, `q`, one closed-value parameter per filter and `sort` (`field` or `-field`), through a `*Query` type both adapters implement; unknown values are `400` JSON, never ignored (ADR 0018). Sort only by non-null columns ending in the id, so the keyset cursor stays valid. Bind search text with `strpos`, never `LIKE`.
- Money is exact decimal (`rust_decimal` / `NUMERIC`), never floats (ADR 0003). In `domain` it is `Amount`: strict parsing, never rounded, no trailing zeros; the API sends and takes decimal strings, and the web app never converts one to a `Number` (`web/src/lib/decimal.ts`).
- Categories are a tree (ADR 0012): only a root chooses the DRE and cash-flow groups, a subcategory inherits them, and the parent and groups never change. The category for transfers is the root in the `transfers` group, found by that group and never by its name. An active category is never under an inactive one (checked by the use case, not the database). The group keys are stored in CHECKs and the audit trail; do not rename them.
- The cash flow (ADR 0032, `BalanceService::cash_flow`, `GET /cash-flow?from=&to=&granularity=&account=`) is composed from the ports like the balances: per account, `cash_by_day` (entries' port) and `movement_by_day` (transfers' port) from the account's opening day, then cut into day or calendar-month periods in the use case, with a running balance that starts from the balance of the day before `from` and takes each opening balance in on its day. The forecast is `open_by_due_day` (what is left of installments, by due date), only for every account together (an installment has no account), and what fell due before `from` is `past_due`, counted by the projected balances. At most 400 days or 60 months (`InvalidSpan`, `400`); the client sends the dates.
- The reports (ADR 0035, `FinancialEntryService::report` and `overdue`, `GET /reports/entries` and `/reports/overdue`, `finance`, read only) are sums made by the entries' port (`report_entries`, `overdue_installments`) in SQL and in memory: the entries grouped by category, cost center or party over a span `from`..`to` (both required: the server reads no clock), on the **competence** basis (the entries whose competence date is in it, by their total) or the **due** basis (the installments due in it, by their amount); rows biggest first and what has no cost center or party last (`sort_report`), amounts as entered and not as settled. The overdue list is the installments due **before** `on` with something left (amount less the settlements that are not reversed), oldest first, cut at `limit` (100 by default, 500 at most) with the totals of all of them.
- An attachment (ADR 0036, `Attachment`, `AttachmentService`, routes under `/entries/{id}/attachments`, `finance`) is a record in `entry_attachments` (name, listed type, 1 byte to 10 MB, `removed`) whose **bytes live in a `BlobStore`** (`LocalBlobStore` in `ATTACHMENTS_DIR`, `InMemoryBlobStore`) under the company and attachment ids, never a typed name. It is never edited or deleted: removing marks it, drops the bytes and audits both. The bytes are written before the record (a failed record write takes them back) and dropped after it is marked. The file is the **body of the request**, its type the `Content-Type` and its name `?name=` (no multipart); a download is always `attachment` with `nosniff`. At most 20 per entry, counted by the use case.
- The lines of a quote, sale or contract (ADR 0037, `Line`, `LineDraft`) are a product, a description kept as typed, a quantity above 0 with at most 3 decimals, a unit price with at most 6 and a discount in cents; a line is worth `round_to_cents(quantity x price) - discount` (the one rounding rule of sales, half away from zero, in `domain`; `web/src/lib/saleLines.ts` does the same in `bigint` and a test holds them to the same cases), and a document's total is the sum of its lines and is never stored. A document has 1 to 100 lines, replaced as a whole with the document in one transaction. Numbers (`Quote`, later `Sale`) are the company's own sequence, taken from `document_counters` inside the write that uses them (`next_document_number`), so a failed write gives its number back. What a document (sales or purchases) points at is asked through `DocumentReferences` (`RegisterDocumentReferences`), and only a reference an edit changes is checked.
- A quote (ADR 0038, `Quote`, `QuoteService`, routes under `/quotes`, area `sales`) is a draft, sent, approved, declined or converted. Changing a sent quote makes it a draft and takes its link back; sending again makes a new link; an answered or converted quote is fixed (`409`). Every write names the status it was made from (`QuoteChanged`, `409`), and the customer's answer (`QuoteRepository::answer`) writes only the status and only through the same link, so it never overwrites an edit nor approves what was changed and sent again; whether a quote changed is decided on the quote (`after == before`), never on the audit text. The link is `{PUBLIC_URL}/quote/{token}` with only the SHA-256 digest of the token stored, shown once in the send's answer; the public routes show no id of the company's books, approve or decline once, refuse an approval past `valid_until` (`410`; a decline is still allowed, and sending an expired quote is refused), judged against **yesterday by the UTC clock** (`customer_today`: UTC turns the day at 21:00 in Brazil; the one place besides the recurrence job where the server reads the clock), answer with `no-store` and `no-referrer` and record it under whoever sent the quote with an `answered_by` change (the trail never holds the customer's e-mail address). The PDF is written by hand in `api/src/quote_pdf.rs` (WinAnsi, tested byte by byte); the e-mail carries the link only.
- A purchase order (ADR 0053, `PurchaseOrder`, `PurchaseService`, routes under `/purchase-orders`, area `purchases`) is a `draft` (the only state that changes), `approved` (items fixed, worth more than 0), `partially_received`, `received` (derived from the receipts, or by `close`) or `cancelled` (only before anything arrived); its lines are the shared `Line` with the unit price as the unit cost. Transitions write only the status under the order's lock (`set_status`, `PurchaseChanged` `409`). A receipt (`PurchaseReceipt`) is never edited: the adapter stores it with the order locked after checking it has the receipts the values were worked from and that no line takes in more than was ordered; the value of a line is taken **cumulatively** (so partial receipts add up to the line) and stored per item. Each receipt makes one payable (`EntryOrigin::PurchaseReceipt`, unique per receipt, none for a receipt worth 0) split by the payment term from the day it arrived; it is validated before the receipt is stored and `POST .../receipts/{id}/finish` makes what a failure left unmade. A purchase is not cancelled once goods arrived.
- Stock (ADR 0052/0054, `StockMovement`, `StockBalance`, `StockService`, routes under `/stock`, area `purchases`) is **a ledger of movements** per product (`in`, `out`, `adjustment`; signed quantity up to 3 decimals and signed value in cents, a day, an optional origin `(kind, id, line)`, an optional `reverses`), never edited or deleted: undoing writes another with the opposite quantity and value (unique index per reversed movement), and one movement per origin and line (partial unique index) makes every document step idempotent. Balances and the **weighted average cost** are added up on every read, never stored; **every valuation lives in `StockMovement::new`/`StockBalance`** (an `in` takes the document's value or quantity × unit cost to the cent; an `out` takes `round_to_cents(V × q / Q)`, or all of `V` when it takes the whole balance, or 0 from a balance at or below zero; an adjustment up is valued at the average), the adapters only compare and store: `record(movements, seen balances, floor, audits)` locks the products (`FOR NO KEY UPDATE`, in id order, in a statement of its own), reads the balances in the next, refuses `StockChanged` if they differ from `seen` (the use case reads again and retries a few times) and `StockInsufficient` under `StockFloor::Zero`, all or none. Sales, purchases and returns reach it through the `DocumentStock` trait (a generic of `SaleService`, `ContractService` and `PurchaseService`): completing a sale writes its exits **last** (after the receivable) and undoes them at once if it was cancelled meanwhile; cancelling reverses the exits before the status is written; a return puts back **at the cost the sale took**, cumulatively; `POST .../receipts/{id}/finish` makes the payable and the stock entries. Only a product of kind `product` has stock. A manual exit or adjustment down never takes the balance below zero; a sale may (ADR 0055 adds the block). Reversal of a movement a document made goes through the document; the day of an automatic reversal is the original's (the server reads no clock).
- Minimum stock and the block (ADR 0055): `GET /stock/alerts` is derived on every read (active products with a minimum and less than it, never stored). `stock_settings` (one per company, audited as a whole, `GET/PUT /stock/settings`, off by default) makes `DocumentStock::ensure_available_for_sale` run **before** a sale is marked completed (quantities summed per product over the lines) and the exits be written with `StockFloor::Zero`; the refusal is `ApplicationError::StockInsufficient { product, available }`, a `409`, so a blocked sale stays open. A contract cycle the stock cannot cover is not billed and is retried by the hourly job.
- An inventory count (ADR 0056, `InventoryCount`, `InventoryCountService`, routes under `/inventory-counts`, area `purchases`) is `open` (the only state that changes), `applied` or `cancelled`, with 1 to 500 lines of a product that has stock, counted once, with **only what was found**; what the books hold is read when it matters (`CountStock`, a second narrow trait `StockService` implements). Applying writes the adjustments **first and once** (origin `inventory_count`, the count's id and line; the difference is worked out inside the write loop against what the stock held **through the day of the count** (the adjustment is booked on that day), 0 apart writes nothing; a count with adjustments written is not edited or cancelled) and sets the status **after**, so asking again finishes it; a line that agreed writes nothing, which is why a repeat after a failure may adjust it if the stock moved.
- Purchase entry from an NF-e (ADR 0057, `parse_nfe` in `infrastructure`, `Invoice` in `domain`, `PurchaseService::preview_invoice`/`enter_invoice`, `POST /purchase-imports[/preview]`, area `purchases`): the XML is **only parsed** (no network, no SEFAZ): 1 MiB limit before the parser, UTF-8, `roxmltree` with the DTD refused (no entity is ever declared), a node limit, only a normal model-55 invoice; the parser returns plain text (`InvoiceDraft`) and **every rule is the domain's** (access key with the right check digit and naming the issuer, series and number; items add up to the totals; the invoice's value formula; installments add up to the value; quantities with at most 3 decimals). An item costs its products less discount plus its charges (freight, insurance, IPI, ICMS ST...), and what the invoice charges that no item carries is shared in proportion so the costs add up to the invoice; a line is worth exactly its cost (unit cost rounded up to six decimals, the cents over taken as discount). **The order carries the access key (unique per company) and is the claim**; entering again finishes whatever a failure left, step by step idempotent (`200 already_entered`, first time `201`); the receipt is paid on the invoice's installments (`purchase_receipt_installments`) or by the payment term. The supplier must be registered and each item must find a product by SKU or be mapped (`422`).
- An inventory count can start from a **spreadsheet** (`openCreate("inventoryCount", { viaSheet: true })`, `lib/countSheet.ts`, `lib/csvRead.ts`): the sheet is read **in the browser** (no endpoint), a column of SKUs (matched without case or accents) and one of what was found (a blank is not counted yet; "SKU"/"Código" and "Contado"/"Quantidade" are the headers), and **fills the form's lines**, which the person reviews and the form checks like anything typed before `POST /inventory-counts`; what cannot be used is said by line. "Baixar modelo" gives the active products with an empty Contado column.
- The NF-e entry sheet goes in **five steps** (`Stepper`, `PurchaseImportForm`): the file, what the invoice says (an unregistered supplier or an invoice already entered stops it here), the nature of the purchase (category, cost center, the payment term only when the invoice gives no installments, the day it arrived), the products of the items (each item needs one) and a last look that says what will be made; nothing is sent to the API until the last button, and a step that cannot go on says why. The values live in the component's state, not in an uncontrolled form, because a step that is left is unmounted. No endpoint changed.
- Ticking orders on the purchases list (writers only) offers **Aprovar** (drafts) and **Cancelar** (drafts and approved) on all that are ticked, **in the browser, one order after the other through the ordinary endpoints** (`BULK_ELIGIBLE`): there is no bulk endpoint, so each order is checked and audited on its own, the others that do not apply are left alone, a confirmation comes first and what failed is named. Closing and receiving are not bulk actions (they need a decision per order).
- Column choosers (`useColumns`, `ColumnChooser`, used on the purchases list and the stock position): which optional columns a table shows is a **per-person convenience kept in `localStorage`** under `conta-verde.columns.{name}` (the names of the hidden ones; blocked or garbled storage falls back to the usual columns, and a key that is no longer an optional column is forgotten), never sent to the server. A table's required columns are not offered, `hiddenByDefault` marks the ones that start off, and a panel row's `colSpan` follows the columns shown.
- The purchases list also narrows by the day an order was **made** (`from`, `to`, both included, either optional, `PurchaseOrderQuery::ordered_from`/`ordered_until`, in the list and in the status counts), shows the expected day and the NF number (the 9 digits of the access key after the model and series, `web/src/lib/invoice.ts`), and uses the shared `PeriodFilter`; `wholeDate` (`web/src/lib/entryInstallments.ts`) keeps a half-typed year out of a request.
- List tiles with counts (stock position and purchases): the numbers come from the server and are never counted on the loaded page. `GET /purchase-orders/status-counts?q=` (`PurchaseOrderRepository::count_by_status`, one `push_filters` shared with the list in Postgres, the query's own status ignored) and `GET /stock/positions/summary?q=&on=` (`StockService::position_summary`) follow the search but never the tile chosen, so every tile keeps its number. `GET /stock/positions?situation=in_stock|below_minimum|depleted` filters by `StockSituation` (domain: quantity above 0, under a set minimum, 0 or less) by scanning the products in order until the page is full. The web `FilterTiles` + `useCounts` read the counts again when the rows change. The ledger's tiles are the same: `GET /stock/movements/kind-counts?product=&from=&to=` (`StockMovementRepository::count_by_kind`, `any_kind`, one `push_movement_filters` shared with the list) never takes the kind or paging parameters.
- Stock reports (ADR 0058, `StockService::valuation` and `movement_summary`, `GET /stock-reports/valuation?on=` and `/movements?from=&to=`, area `purchases`, read only) are derived on every read from the products' and the movements' ports (`balances` through a day; `totals_by_product` sums by kind in SQL and in memory), the day is the client's (the server reads no clock) and a movements span is at most 366 days (`400`); the valuation lists products with something on hand or some value, biggest value first, with the share of the total and the count with a negative balance; opening + entered - exited + adjusted = closing, a reversal counting under the opposite kind.
- A sale (ADR 0039, `Sale`, `SaleService`, routes under `/sales`, area `sales`) is an `open` order (the only state that changes), a `completed` sale or a `cancelled` one. Completing validates the receivable first (`FinancialEntryService::validate`), then marks the sale, then writes the entry with origin `EntryOrigin::Sale`; a unique index gives a sale one entry, so completing is idempotent and asking again finishes an entry a failure left unmade. The receivable is split by `PaymentTerm::split` (each share cut to the cent, the last takes the remainder; none without a term: one installment on the sale's day; `web/src/lib/termSplit.ts` previews it with the same cases). An entry can be cancelled once and for good (`voided`, `FinancialEntryRepository::void`, `FinancialEntryService::void`): refused while a settlement is not reversed (`EntrySettled`), out of the open amounts, the overdue list and the reports by group in **both** adapters, listed with `voided=true|false`, never edited or settled; cancelling a completed sale voids its receivable first and is refused while it has settlements or returns. A transition writes only the status (`SaleRepository::set_status`, under the sale's lock, cancelling refused with `SaleHasReturns` there), and a return is stored only while the sale is completed and has the returns the refund was worked from (`save_return(known_returns)`); what a sale or a return made is not edited as an entry (`EntryFollowsASale`). The lines in the audit trail are one per row (`\n`), the description last. A return takes back at most what was sold and not returned (checked by the adapter with the sale locked), refunds each line cumulatively rounded, and makes a payable with origin `SaleReturn` (the return is stored first, so only a storage failure leaves one without its refund); it never reduces the receivable. `EntryOrigin` is an enum (`Recurrence`, `Sale`, `SaleReturn`) with a CHECK of at most one origin and a unique index per origin (`DuplicateOrigin`). A quote becomes one sale (`POST /quotes/{id}/convert`, a unique index on `sales.quote_id`; asking again gives that sale).
- A contract (ADR 0040, `Contract`, `ContractService`, routes under `/contracts`, area `sales`) bills each cycle **on its day** as a completed sale (`SaleService::bill_cycle`): `starts_on` plus 0, 1, 2… cycles of 1, 2, 3, 6 or 12 months by `CalendarDate::plus_months` (the day clipped, never slid), at most one sale per cycle day (unique index on `sales (contract_id, cycle_on)`, `DuplicateCycle`), and a cycle that already has its sale is only finished, so a pass is safe to repeat and to run twice. It runs when a contract is written (server `today()`) and in an hourly task in `main.rs`; `bill_all_due(day)` takes the day, so tests move the clock, and its report counts the contracts of every company (assert on one company's sales, not on the report). `billed_through` is bookkeeping written without an audit entry; a paused contract that is brought back goes on from today; a terminated one is fixed (`ContractIsTerminated`, `409`) but still bills the cycles due up to its last day; a cycle whose sale was cancelled is consumed; the job re-reads each contract and bills up to `customer_today()`. `adjust` raises every unit price by a percentage rounded to the cent (`round_to_cents`) for the cycles billed from then on. The sales are made in the name of whoever last saved it.
- A commission rule (ADR 0041, `CommissionRule`, `CommissionService`, routes `commission-rules` and `GET /commissions?from=&to=&seller=`, `sales` area) is a rate (above 0 to 100, two decimals) for one seller or all and one product or all, over the sale days `starts_on`..`ends_on`; it is replaced as a whole by `PUT` (`active` required), never deleted, and **a new rate is a new rule that starts later**. The rule for a line is the narrowest that covers the sale's own day (seller and product, seller, product, general; ties by later start, then id; inactive ignored). The statement is computed on every read, never stored, from the completed sales **with a seller** sold in the span (both dates required, at most 2000 sales) through the sales' port (`sold_between`, `returns_of_sales`), per line `round_to_cents(net × rate / 100)` with the net being the line less its cumulative refund; a line no rule covers earns nothing but counts in the base.
- A price list (ADR 0042, `PriceList`, `PriceListService`, routes `price-lists`, `sales` area) is a name (unique per company, ignoring case), an `active` flag (required when replacing) and 1 to 1000 prices (a product once, a unit price of at most six decimals), replaced as a whole with the list in one transaction (`price_list_items`, composite company FKs). Only a product a change adds must be usable. It is **not part of any document**: lines keep the price they were filled with, and the web `LinesEditor` fills a line's price from the list chosen (falling back to the product's sale price) on the client, without sending the list.
- A sales report (ADR 0043, `SalesReportService`, `GET /sales-reports?by=customer|product|seller&from=&to=`, `sales` area) is added up when read from the completed sales of a span net of returns (both dates required, at most 2000 sales, composed from the sales' port like the commissions and never as SQL in two adapters). The net of each line is the one domain function `net_of_lines`, shared with `commission_of_sale`. Rows are biggest first (no seller last), with their share and cumulative share (two decimals) and an ABC class given by the cumulative share **before** the row (A under 80%, B under 95%, else C), worked out from the exact values.
- A charge (ADR 0045, `Charge`, `ChargeService`, routes under `/entries/{id}/charges` and `GET /collection`, `finance`) asks a **payment provider** (`PaymentProvider` port; `FakePaymentProvider` and the off `NoPaymentProvider` in `infrastructure`, picked by `PAYMENT_PROVIDER` in `main.rs`: unset or `off` means no collection, an unknown name stops the server) to collect what is left of one installment of a receivable that is not cancelled and has a customer, and keeps what the customer pays with: a digitable line, a Pix copy-and-paste text or an https address, each method with its own and nothing of another's (domain and `CHECK`). At most one charge per installment is `open` (unique partial index, `ChargeAlreadyOpen`); it is never edited or deleted, only cancelled (at the provider first, and only with the provider that made it) or, from the webhooks of ADR 0046, paid or expired. It records who issued it, because what it settles later is settled in their name. If storing the charge fails the provider's is called off. A `ProviderError`'s text goes to the log and never to a client. Tests use the fake provider, never a real one; credentials of a real adapter come from the environment and are never stored or logged (ADR 0044).

The port has `submit_nfse`, `query_nfse` and `cancel_nfse` only (`DocumentOutcome<D>` is generic; the national NFS-e has no correction letter nor invalidation, so `correct` refuses it). **Focus NFe builds it from its documentation, never exercised; NFE.io answers `Unsupported` and sends nothing** (its published reference does not say how to find an invoice by our reference): do not make it submit without a file that settles that. The package carries it in the same columns, `fiscal/nfse/{key or number}`. The Documentos page issues it through `ServiceIssueForm` (`components/FiscalServiceIssueForm.tsx`: no default, only a service nature with terms), names it by `documentLabel` (its number, or `DPS series/number` while it waits) and offers it no correction letter.
- A fiscal document (ADR 0076, `FiscalDocument` in `domain`, `FiscalDocumentRepository`, tables `fiscal_documents` and `fiscal_files`, `FiscalDocumentService`, routes under `/fiscal/documents`; the events (`FiscalEvent`, `fiscal_events`) and the **Documentos** page (`pages/FiscalDocumentsPage.tsx`, `components/FiscalDocumentSheet.tsx`, `FiscalIssueForm.tsx`: the six tax choices start empty, the buttons that write follow `useCanWrite("fiscal")`) are in) is an NF-e of a sale on its way to or past the authority: **draft, processing, authorized, contingency, rejected, denied, cancelled**, every move a method of the domain type that refuses what the states do not allow, and **our id is the gateway's reference**. It keeps the totals and the authority's answer, **not the lines** (they are in the signed XML). **Its content is frozen once authorized** (the adapters refuse a different one and a Postgres trigger forbids it, as it forbids deleting a document or a file), **a sale has one live document per kind** (partial unique index; a rejected, denied or cancelled one frees it) and an access key names one document of a company. The XML and the DANFE are in the `BlobStore` keyed by `BlobId` (an `AttachmentId` converts into it and keeps its place on disk), recorded in `fiscal_files` (one per document and kind, written after the bytes, never replaced or deleted). `GET /fiscal/documents` lists newest first by the moment of issue (`limit`, `after`, `status`, `sale`; no `q` or `sort`). Adapter behavior is `contract::fiscal_documents_are_kept` and `contract::issues_an_nfe_from_a_sale`. **Issuing** (`IssueNfe`: sale, nature, origin 0 to 8, buyer presence, payment form, final consumer, **every one chosen by the person, none defaulted**) refuses before sending when there are no settings, no gateway, a regime other than Simples Nacional, a certificate day passed, a sale not completed, a product with no NCM, a customer with no document or address, or an item no tax rule covers (`422`, naming the item); the CFOP is the nature's for the issuer's state or for another by the customer's address; asking twice finds the sale's live document and asks the gateway; **`Unknown` or a refusal that sent nothing makes the document `rejected`** and the person sends it again under the same id (`POST .../resend`, built again from the sale); an unreachable gateway leaves it `processing`. Files are written before the status that names them; cancelling asks the gateway first, needs 15 to 255 characters and is `409 PeriodLocked` for a closed issue day; a late authorization is written with a note. **Events** (a correction letter or a cancellation of an authorized document, an invalidation of a range of numbers; `correct`, `invalidate`, routes `/corrections`, `/fiscal/invalidations`, `/fiscal/events/{id}/file`) are **recorded as `sent` before the gateway is asked** and settled once to `accepted` or `refused`, never changed or deleted (trigger); an answer that never came leaves the event `sent` and **it is never sent again**, and a new letter waits for it; a document takes at most 20 *accepted* letters (the place is our own attempt count, up to 99) and a letter needs the document still `authorized` when it is recorded; `abandon_event` is the person's way out of a `sent` event; a number a document of the company holds is never invalidated; adapter behavior is `contract::fiscal_events_are_kept`. The accountant's package (`FiscalDocumentService::package`, `FiscalDocumentRepository::issued_between`, `fiscal.csv` and `fiscal/nfe/{access_key}...`) holds the **production** documents issued in the span that are authorized or cancelled, their XML, DANFE, cancellation XML and accepted letters' XML, counted with the attachments against the same limits before any file is read; its columns are fixed (ADR 0076). The poll is a once-a-minute pass over `pending(since, limit)` in `main.rs`, in the name of whoever submitted, never a job.
- A recurrence (ADR 0033, `/companies/{id}/recurrences`, `RecurrenceService`) is a register that becomes ordinary entries with one installment each, up to 60 days ahead of today, never past `ends_on`: `starts_on` plus 0, 1, 2… periods, a month counted **from `starts_on`** with the day clipped (the 31st is never slid to the 28th for good). The entry carries `recurrence_id` and `occurrence_on`, and a **unique index** makes at most one per occurrence day, so generating twice or in two places is safe (`DuplicateOrigin` is skipped); entries are made in the name of whoever last saved the recurrence (no system actor in the audit trail yet), and `generated_through` is bookkeeping written without an audit entry. It runs when a recurrence is saved (the server's UTC `today()`, the only place the server reads a clock) and in an hourly task spawned in `main.rs`; there is no `jobs` table because the pass is idempotent. A recurrence whose entries cannot be made (its category was deactivated) is skipped and retried, the others go on.
- Bank accounts keep no balance: it is added up on every read (ADR 0031) from the account's opening balance (its own record, signed, set by `PUT .../opening-balance`), the cash of its settlements that are not reversed (receivable adds, payable takes off) and its transfers in and out, counted from the opening day through the day asked (before it the balance is 0, without an opening everything counts). `BalanceService` composes it from the ports (`FinancialEntryRepository::cash_of_account`, `TransferRepository::movement_of_account`), never one query across tables, so both adapters answer alike; `GET /balances?on=` takes a required date because the server never reads a clock. A transfer moves money between two usable accounts, is not an entry (no category, nothing in the income statement), and like a settlement is reversed, never edited or deleted. Their branch and number are stored in one form (upper case letters and digits, no punctuation) because a unique index and, later, OFX matching depend on it; never store them as typed. Their kind, like a product's, is fixed once registered (ADR 0021).
- A financial entry (ADR 0029) has one category (active, never the transfers one), an optional cost center and party, a competence date and 1 to 120 installments (a due date that never decreases, an amount above 0 in cents); its total is the sum and is never stored. It is replaced as a whole by `PUT`, and the use case checks what it points at through `EntryReferences` (`RegisterReferences` asks the registers' own ports, so one implementation serves Postgres and memory: the in-memory registers are `Clone` over an `Arc` for that), while the database refuses a reference to another company with composite foreign keys. Dates are `CalendarDate` (`YYYY-MM-DD`, no zone, `DATE` in Postgres through text), never a timestamp. There is no delete or cancel yet; what an entry may still change once settled is the next slice's decision.
- A settlement (ADR 0030) pays one installment of an entry: `applied` (the part of the installment it settles, above 0), `interest`, `fine` and `discount` (0 or more, in cents) and a bank account (and optionally a method) that must be usable; the cash is `applied + interest + fine - discount` and is never stored, and neither is an installment's balance. It is never edited or deleted: `DELETE` reverses it (`reversed`), it stops counting and the trail keeps it. The check against the balance, the write and the audit entry are one transaction in the entry's port (`settle`): the installment row is locked **in a statement of its own and the balance read in the next one**, because in READ COMMITTED a sum read in the statement that waits for the lock uses the snapshot from before the wait (a concurrency test found it). While an entry has settlements that are not reversed its installments and kind cannot change (`409`), enforced by the adapters inside `update`. "Overdue" is told by the web app with today's date where the person is; the server never reads a clock for it.
- A payment term's installments are replaced as a whole in the transaction that writes the term and its audit entry, and their sum (exactly 100) and order live only in the domain: the database does not see them (ADR 0021). Percentages are strings with at most two decimals, never rounded; the web form fills equal shares with the remainder on the last.
- A party is replaced as a whole (`PUT`), and the registry is asked about its CNPJ only when the document changed; the same document keeps the old answer. `is_carrier` and `is_seller` must be said when replacing, so an old client cannot drop them. The address is all or nothing, in the domain and in a `CHECK`, and only its shape is checked (ADR 0022). Contacts (up to 20, in order) and tags (up to 10, lower case, no register) are replaced as a whole by the same `PUT`, must be said when replacing, and are read with the party in one `REPEATABLE READ` snapshot (`postgres::snapshot`); whether the contacts changed is decided on the contacts, never on the audit text (ADR 0023).
- A new register copies the products one (ADR 0019): a domain type that validates and normalizes, a port with a contract test (scoping, atomic audit, refused writes leave no trace), an adapter pair, a `PUT` that replaces and audits only the difference, and a `CHECK` in the migration for every domain rule so the database refuses what the domain would. The migration repeats the rules one row can show (shapes, key lists, lengths, uniqueness), not those that span rows, and its comments and the docs say which is which. A value the domain accepts must be one Postgres accepts too (NUL bytes were the case that bit).
- SQL uses runtime `sqlx::query`, not `query!` macros. Do not add `query!` without also solving offline data for CI.
- A new adapter or port method needs both adapters (Postgres and in-memory) to behave the same, including ordering.

## Gotchas

- Auth is cookie sessions (ADR 0007). Every `/companies/{company_id}/...` handler must take the `CompanyAccess` extractor (before any `Json`/`Query`); missing sessions get `401`, non-members and unknown companies both get `404`, and a member whose role does not reach the route gets `403`.
- An invitation's link carries a 256-bit token whose SHA-256 digest is all the database keeps, is shown once, and gives nothing by itself: accepting needs the session of the address it was sent to, or a sign-up through the link (`invitation` instead of `company_name` in `POST /auth/register`, which makes no company of its own) (ADR 0027). `GET /invitations/{token}` and the quote routes under `/public/quotes/{token}` (ADR 0038) are the only routes that need no session. Sending the e-mail never fails the invitation (`EmailSender`, ADR 0014; it is queued and sent by the worker, ADR 0059): `SMTP_URL` and `SMTP_FROM` (both or neither, or the server does not start) send it through `SmtpEmailSender`, and without them the log adapter only logs it and says it was not sent, and the log then holds the link. Tests never reach a mail server: use `InMemoryEmailSender` or the fake SMTP server in `smtp_email_sender.rs`. An e-mail is an `EmailContent` (ADR 0068: heading, paragraphs, details, items, notice, note, button) sent with `send_content`, never a string: the text part comes from it everywhere and `BrandedEmailSender` adds the HTML layout (`SOURCE_URL` in its footer, AGPL section 13); tests assert the facts in `body`, not its shape. Tokens come from `SecretService::new_token` and are stored as `digest_token`, never raw.
- The accountant (ADR 0067) is the `accountant` role: invited like any member, reads every area but `members` and writes only the `accounting` area (the period lock, the exports, the schedule of the monthly package; owner and admin write it too, everyone else reads it). `access::SEGMENT_AREAS` is the one table of route segments; a test walks **every route of the router** (read from the source of `router`) with the accountant and the viewer and expects `403` on each write outside `accounting`.
- The period lock (ADR 0069, `PeriodLock`, `PeriodLockService`, `GET/PUT /accounting/period-lock`, `accounting` area) is one date per company, the last day of a month: **a write that makes, changes or undoes what the books hold on a day on or before it is `409` `PeriodLocked`**, checked in the use case before the first write, never in a trigger. The date that locks each record is in the ADR (competence for an entry, `settled_on`, `occurred_on`, `sold_on`/`returned_on`, `received_on`, the movement's day and, to undo one, the original's). A new service that writes a dated record asks `EntryReferences::ensure_open` (`FinancialEntryService::references()` gives it); `StockService` and `BalanceService` take the lock port with `with_period_lock`, and the API's `Ports::PeriodLocks` makes the wiring name it. Drafts, quotes and attachments are not locked; reopening needs a reason, kept in the trail; a payment webhook on a closed day is kept paid with a note. Every adapter's behavior is `contract::a_closed_month_refuses_*`.
- The DRE (ADR 0070, `DreService`, `GET /dre?from=&to=&by=month|cost_center&cost_center=`, `finance`, read only) is derived on every read from `FinancialEntryRepository::competence_totals` (entries not cancelled, by **total**, per month, category and cost center) and the categories' DRE groups: a receivable counts positive and a payable negative, `DreLines` in `domain` works the subtotals out and keeps `investments` and `outside_result` below the line, an empty month is a zero column, at most 24 months, both dates required (the server reads no clock). A report that needs a DRE group asks `DreService`, never joins categories in an adapter.
- The accountant's exports (ADR 0071, `AccountingExportService`, `GET /accounting/exports/{entries,settlements,transfers,package}?from=&to=&format=csv|xlsx`, `accounting` area, read only) are made from the ports as plain tables (`ExportTable` of text and amount cells) and **drawn in `api/src/export_files.rs`**, by hand and with no new crate: a CSV like the web app's (BOM, `;`, formula cells quoted), an XLSX of five parts with amounts as numeric cells holding the decimal text, a zip stored without compression with a fixed 1980 timestamp. **The column layout of each file is in the ADR and does not change without a new ADR.** Cancelled entries and reversed settlements and transfers are left out, amounts are never negative (a `kind` column says the direction), names include inactive records (`ExportLookups`, which `RegisterReferences` implements). Limits are 366 days, 50,000 rows per file, 500 attached files and 200 MiB, checked from the records before any file is read, and answer `400`/`422`, never a cut-off file. An attachment's path in the zip is `attachments/{entry}/{id}-{name}` with what Windows cannot unpack (`/ \ : * ? " < > |`, control characters) turned into `_`, and the list and files follow the order of the entries file. The package is built in `spawn_blocking` with the files moved, not copied. The product keeps no XML of the purchase invoices it enters (ADR 0057): of what comes in, the package carries only what was attached to an entry; **the fiscal documents it issues (production, issued in the span) are in it too, with `fiscal.csv`** (ADR 0076, amending this).
- The monthly package notice (ADR 0072, `PackageSchedule` in `domain`, `PackageScheduleService`, `GET/PUT /accounting/package-schedule` and `/history`, `accounting` area) is a switch and a day of the month **1 to 28**, one per company, audited as a whole (`enabled` and `day` required when replacing; off on the 5th until chosen). An **hourly pass** (`announce_monthly_packages`, `send_due(today, now_millis)`: the day is `customer_today()`, tests move it) announces the **previous month** (`month_to_package`) from the chosen day to the end of the month to **every member whose role is `accountant` and nobody else**, through the queue: the e-mail says the package is ready and has one button to `{PUBLIC_URL}/companies/{id}/accounting?month=YYYY-MM`, the **login-gated** Contador page; **never attach the files or put a link that works without a login in it**. A month goes out once because `PackageScheduleRepository::claim` inserts `(company, month)` in one statement before anything is queued; it is `release`d only when **nothing** was queued (some queued would be sent twice), and a company with no accountant is not claimed. Each company's turn is isolated (an error is logged and the others go on; what can fail is read **before** the claim) and with e-mail off (`EmailSender::is_enabled`) the pass claims nothing. The pass reaches every company of a database, so a test that shares one asserts on its own recipients and uses months no other test does.
- What a role may do is decided by `CompanyAccess` from the **route**, not by the handler (ADR 0026): the area is the segment after `{company_id}` and the access is the method (`GET` reads, anything else writes). A new family of company routes needs its segment added to `SEGMENT_AREAS` in `access.rs`, or it is refused to everybody (`quotes` and the other sales segments are in the `sales` area, ADR 0037); the table is `Role::access_to` in the domain, and the web app reads `permissions` from `/auth/me` instead of knowing it: a register page gates its form, import and edit buttons on `useCanWrite(area)` (`web/src/lib/useCanWrite.ts`), which only spares the person a refusal.
- A limit and a log for those e-mails (ADR 0065, `document_mails`, `DocumentMailRepository::reserve`/`release`/`of_document`, `GET .../mails`): what was sent is a log (not audited, no foreign key to the polymorphic document), the **same document is not sent again to the same address within 5 minutes and a company e-mails at most 100 documents a day** (`COOLDOWN_MILLIS`, `DAILY_CAP` in the domain; `429` saying which). The check and the record are one atomic step (an advisory lock on the company in Postgres), the send follows, and a send that was not taken **releases** its record. The caller passes the moment (`MailAsk.now_millis`, `now_millis()` in the API) so a test moves it.
- Documents by e-mail (ADR 0061, `DocumentMailService`, `POST /purchase-orders/{id}/send` and `POST /entries/{id}/settlements/{id}/receipt`) are mailed **on request**, as text through the queue, and write nothing (no audit): a purchase order only when `approved` or `partially_received`, a receipt only for a settlement of a receivable that was not reversed (`409` otherwise). The address is `to` or `Party::address_to_write_to` (own, else the first contact's), `422` when there is none; the answer is `{to, emailed}`. Names go through `one_line` before they reach a subject or body; amounts are written `R$ 10,25` and days `dd/mm/aaaa`.
- A password reset (ADR 0060, `MemberService::request_password_reset`/`reset_password`, `POST /auth/password-reset` and `/confirm`, no session) answers `202` for any address and e-mails a link `{PUBLIC_URL}/reset-password/{token}` through the queue; only the token's digest is stored (`password_resets`, up to five per user, an hour, single use, spending one ends them all), no new link inside a minute of the last, a spent link is `410` and ends **every session** of the account.
- An address held by an account **nobody confirmed** is released only to whoever proves the mailbox (ADR 0066): a sign-up that finds it taken (`409`) sends the address the ordinary password reset link (`MemberService::recover_unconfirmed_address`; the holder confirmed gets the plain refusal and no mail), and spending the link hands the account to the mailbox's owner. Nothing is deleted and nothing is released without that proof. `reset_password` also checks the link (`IdentityRepository::password_reset_open`) before it hashes the password, so a made-up token costs no Argon2 work.
- Address confirmation (ADR 0063, `users.email_verified_at`, `email_confirmations`, `MemberService::send_email_confirmation`/`confirm_email`, `POST /auth/email-confirmation` with a session and `/confirm` without, `email_verified` in `/auth/me`): a sign-up with a company of its own mails a link (3 days, single use, up to five out, a minute apart, spending one deletes the rest); one through an invitation is marked confirmed at once. It is a **request, not a gate**: the web app shows a banner until it is done, and the confirm page needs a button press so a mail scanner cannot spend the link.
- Account notices (ADR 0062, `MemberService::notify`): a spent reset link also mails the owner of the address that the password changed (`reset_password` returns whose it was; `IdentityRepository::find_user`), and an accepted invitation mails whoever sent it. Both go through the queue and never fail what caused them. A notice per sign-in is deliberately not sent (no device tracking).
- Not built yet: login rate limiting, handing a company over. A company has one owner, never changed or removed, which is what keeps it from being left without one (ADR 0028); `PATCH`/`DELETE /companies/{id}/members/{user_id}` change a role or end a membership, and the adapters refuse the owner themselves (`role <> 'owner'`). The API still binds to `127.0.0.1` by default and needs a TLS proxy plus `COOKIE_SECURE=true` before being exposed. Do not change the default bind address.
- The foreign key `parties.company_id -> companies` fails on old dev databases holding orphan parties: `docker compose down -v` resets it.
- Secrets (Argon2, token generation and digests) sit behind the `SecretService` port; the `argon2` crate is optimized even in dev builds (workspace `Cargo.toml`), or tests would take seconds per login.
- Migrations live in `crates/infrastructure/migrations/`. Do not edit one that has been merged to `main`; add a new one.
- Editing an applied migration locally breaks your dev database checksum: `docker compose down -v` resets it.
- Companies that have audit rows cannot be deleted in a dev database: `audit_log` references them and a trigger forbids deleting or updating its rows. Reset with `docker compose down -v` instead of `DELETE`.
- Storage errors are logged server-side and returned to clients as a generic `internal error`. Keep it that way.
- Documents are stored without punctuation and validated with check digits in `domain`: a CPF is 11 digits; a CNPJ is 14 characters whose first 12 may be uppercase letters (alphanumeric CNPJ, since July 2026). Never assume a document is numeric (no `inputMode="numeric"`, no digit-only parsing).
- A CNPJ is also looked up in the federal registry (ADR 0017); a CPF never is. Nothing the registry says blocks a registration: `NotFound` stores the party as `NotFound` with a warning (its data lags, so new companies can be missing), an outage stores it as `Unverified`, and `CNPJ_LOOKUP=off` (`Disabled`) stores it as `NotApplicable` without nagging. The port takes a `Cnpj`, which only `Document::cnpj` can build. Tests must never call the real service: use `InMemoryCnpjRegistry` or the local fake in `brasil_api.rs`. The real BrasilAPI answers 429 to requests without a `User-Agent`, and to callers that exceed its rate limit.
- An import (ADR 0025, parties and products, one pipeline `import_rows` in `application`) checks every row before writing any, refuses the whole file if one row is refused, then writes row by row (each with its own audit entry) and **skips** a row whose document or SKU is registered, never overwriting. A price may use a decimal comma (`12,50`) and nothing else beyond the strict amount. It does not ask the CNPJ registry (`Unverified`, or `NotApplicable` when `CnpjRegistry::is_enabled` is false). CSV is read in `api` (`csv_import.rs`); use cases take drafts and know nothing of CSV.
- A CEP is looked up only when the person presses "Buscar endereço" (ADR 0024): `GET /companies/{id}/postal-codes/{code}`, nothing stored or audited, `CEP_LOOKUP=off` switches it off. BrasilAPI answers `404` both for an unknown code and when its own sources are down, so a `404` proves nothing; the port takes a `PostalCode`, and a code that is not eight digits is refused before the directory is asked. Tests use `InMemoryPostalCodeDirectory` or the local fake in `brasil_api_postal_code.rs`.

## Conventions

- Reply to the user in Brazilian Portuguese. Code, identifiers, commits, branch names and user-facing docs are in **English**.
- Commits and branches follow semantic prefixes (`feat`, `fix`, `docs`, `refactor`, `chore`, `test`), e.g. `feat/accounts-payable`.
- Comments explain why, not what. No dead code, no premature abstraction.
- Tests before refactoring. Run `pnpm check` before declaring work done.
- Docs under `docs/` start with frontmatter: `title`, `status`, `date`, `tags`. ADRs are `docs/adr/NNNN-slug.md`; record significant decisions as a new ADR.

## Workflow

- Work in a git worktree on a semantic branch, push with `gh`, open a PR to `main` (GitHub flow).
- **Review is local**: run `/code-review` on the branch and fix the findings before asking for merge. Do not wait for the Copilot reviewer.
- Documentation-only PRs (ADRs, `docs/`, CLAUDE.md) may be merged right after the push.
- Use `pnpm` for Node tooling and `uv` for Python, if either is ever needed.
